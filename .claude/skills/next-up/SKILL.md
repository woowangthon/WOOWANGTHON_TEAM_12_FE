# next-up

이슈 담당을 미리 정하지 않고 시간 · 토큰이 남는 사람이 가져가는 방식이라(ADR-002), GitHub의 선행(blocked by) · 하위 이슈 연결을 읽어 **레포별 전체 추천 순서**를 매번 계산한다. 순번 라벨을 붙이지 않는다 — 선행이 끝나면 순서도 달라진다.

## 절차

1. 이 스킬 폴더의 `collect.sh`로 네 레포의 열린 Milestone · 열린 이슈 · 열린 선행 · 열린 하위 이슈를 모은다(어느 레포에서 돌려도 결과가 같다).

   ```bash
   bash .claude/skills/next-up/collect.sh
   ```

2. **지금 스프린트**는 열린 Milestone 중 `스프린트 N`의 N이 가장 작은 것. 설명 칸이 그 스프린트의 목표 흐름이다. 없으면 「열린 스프린트 없음」으로 표시한다.
3. 실제 GitHub 하위 이슈 연결을 거꾸로 읽어 각 작업의 부모를 찾는다. `epic` 라벨 · 비슷한 제목 · SPEC 번호로 관계를 추측하지 않는다. 부모의 담당 · 선행 · Milestone은 자식에게 물려주지 않는다.
   - 열린 하위 이슈가 있는 부모는 추천 대상에서 빼고, 해당 레포 표의 번호 없는 현황 행으로 남긴다. 자식 행의 「기능」 칸에 부모 키와 짧은 제목을 쓴다. 중첩 관계는 `ETC#1 > ETC#2`처럼 표시한다.
   - 열린 하위 이슈가 없는 `epic`은 전체 하위 이슈도 확인한다(`gh api repos/<소유자>/<레포>/issues/<번호>/sub_issues --paginate`). 원래 하위 이슈가 없으면 「계획 필요 · plan-feature로 쪼개기」, 모두 닫혔으면 「잔여 범위 확인 · 하위 a/a 닫힘」으로 표시한다. 새 구현 작업으로 단정하지 않는다.
4. 네 레포를 함께 위상 정렬한다. 열린 선행은 반드시 후속 작업보다 앞에 둔다. 아직 정렬하지 않은 열린 선행이 없는 후보 중 다음 순서로 하나씩 고른다.
   1. 지금 스프린트 → 다음 스프린트(N 오름차순) → Milestone 없음. 다른 이름의 Milestone은 다음 스프린트 뒤, Milestone 없음 앞에 제목순으로 둔다.
   2. 다른 열린 이슈를 많이 풀어 주는 작업 먼저. 직접 · 간접으로 기다리는 열린 이슈를 중복 없이 센다.
   3. `P0` → `P1` → `P2` → `P3` → 우선순위 라벨 없음. Milestone이 없다는 이유로 우선순위를 P2로 바꾸지 않는다.
   4. 위 조건이 같으면 같은 부모의 작업이 인접하도록 부모 키순 → 이슈 번호순. 부모가 없으면 자기 이슈 키를 정렬 키로 쓴다. 키의 레포 순서는 FE · BE · AI · ETC, 번호는 숫자순이다.
   - epic을 붙이려고 선행 · 스프린트 · 풀어 주는 수 · 우선순위를 뒤집지 않는다. 조건이 다른 같은 epic 작업은 떨어져 있어도 기능 칸으로 관계를 보여 준다.
   - 순환이나 수집되지 않은 선행 때문에 정렬할 수 없는 작업은 임의로 순서를 만들지 않고 번호 없이 「순서 확인 필요」와 원인을 표시한다.
5. 이슈마다 상태와 필요한 행동을 붙인다.
   - **지금 가능** — 담당 없음 + 열린 선행 없음.
   - **목으로 먼저** — 담당 없음 + 열린 선행이 계약 이슈(ETC `docs` 라벨 · 제목 「계약」)뿐이고, 본문 「선행 이슈」에 「계약 전엔 … 시작해도 된다」가 명시됨.
   - **진행 중** — 담당 있음. 연결된 열린 PR도 확인해서 담당과 함께 표시한다(`gh pr list -R <레포> --search "<번호> in:body" --state open`).
   - **대기** — 나머지. 열린 선행을 모두 「기다림」 칸에 쓴다. 진행 중 · 목으로 먼저인 작업도 열린 선행이 있으면 표시한다.
   - 계획 필요 · 잔여 범위 확인인 epic은 위 상태에 확인할 행동도 함께 쓴다. 부모 현황 행은 담당이 있으면 「진행 중」, 없으면 「하위 진행」으로 표시한다.
6. 정렬 결과를 **FE → BE → AI → ETC** 순으로 나누고, 각 레포 안에서는 계산한 순서를 유지한다. 진행 중 · 부모 현황 · 순서 확인 필요를 제외한 작업에 **레포마다 1부터 연속 번호**를 붙인다. 전역 추천 번호는 쓰지 않는다. 대기 작업도 번호를 붙이고 선행을 명시한다.
7. 진행 중 · 부모 현황 · 순서 확인 필요 행은 자기 레포 표의 끝에 번호 `—`로 둔다. 같은 행이 여러 조건에 해당하면 한 번만 쓰고 상태를 함께 표시한다. 번호 없는 행도 스프린트 · 우선순위 · 부모 키 · 이슈 번호순으로 고정한다.
8. 본문에 선행이 있는데 수집한 「열린 선행」이 `-`라면 닫힌 선행인지 확인한다. 연결이 빠진 것으로 보이면 끝에 「`plan-feature/link.sh check`로 확인 — 연결이 빠지면 순서가 틀린다」를 쓴다.

## 출력 형식

**추천 3개 요약 없이 레포별 표 하나씩, 전체 작업을 한 번씩 보여 준다.** 기능별 현황 · 독립 작업 · 백로그를 별도 목록으로 다시 나누지 않는다. 스프린트와 우선순위는 각 행에서 읽는다.

아래는 출력 구조를 설명하는 가상 예시다. 실제 출력은 수집한 이슈 · 링크 · 계산 결과로 채운다.

스프린트 2 — 경험 입력: 닫힘 a / 전체 b (네 레포 합계)

- 이슈 · 부모 · PR은 링크로 표시한다. 부모는 자기 레포 현황 행과 자식의 기능 칸에서 연결하되 추천 작업으로 중복 집계하지 않는다. 기능 칸에 부모가 없는 작업은 `—`로 두고 같은 추천 목록에 섞는다.
- 레포 표시 순서는 레포 사이 실행 순서가 아니다. FE 1번과 BE 1번의 전역 우열을 뜻하지 않는다. 「기다림」이 실제 시작 조건이며, 대기 작업을 건너뛰고 가능한 작업을 가져갈 수 있다.
- 사용자가 「FE 쪽」처럼 영역을 지정하면 그 레포 표를 먼저 보여 주고 나머지 표도 유지한다. 각 레포의 순서와 번호는 바꾸지 않는다.
- 열린 이슈가 없는 레포도 제목과 「열린 작업 없음」을 표시한다. 진행 중 작업만 있으면 「지금 가져갈 작업 없음」과 진행 중 행을 표시한다. 모두 대기 중이면 기다리는 이유가 표에서 보이게 한다.
- 열린 스프린트가 없으면 맨 위에 「열린 스프린트 없음」만 쓰고 레포별 표를 계속 보여 준다. 지금 스프린트의 이슈가 다 닫혔으면 맨 위에 「스프린트 N 흐름이 다 닫혔다 — PM이 써 보고 피드백 → 다음 스프린트 SPEC을 채운다(ADR-002)」를 쓴다.

## 경계

- **읽기만 한다.** 담당을 걸거나 이슈 · Milestone을 바꾸지 않는다. 가져가는 건 `implement-issue`가 시작할 때 한다.
- 이어서 `implement-issue`나 `plan-feature`로 자동으로 넘어가지 않는다 — 고르는 건 사람이다.
